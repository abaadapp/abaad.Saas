# Parallel Development Workflow — Abaad

هذا الملف يحدد طريقة العمل المتوازي بين سعد وعدي وChatGPT بدون التأثير المباشر على `main` أو على عمل الطرف الآخر.

## القاعدة الأساسية

- فرع `main` هو النسخة المستقرة فقط.
- ممنوع التطوير المباشر على `main`.
- كل إصلاح أو تعديل أو ميزة تبدأ من أحدث نسخة من `main` في Branch مستقل.
- كل Branch يعالج نطاقًا واحدًا واضحًا قدر الإمكان.
- الدمج إلى `main` يتم فقط عبر Pull Request بعد المراجعة والاختبارات.

## تسمية الفروع

استخدم الصيغة التالية:

- `saad/fix/<short-name>`
- `saad/feature/<short-name>`
- `udai/fix/<short-name>`
- `udai/feature/<short-name>`
- `chatgpt/review/<short-name>`
- `chatgpt/fix/<short-name>`

أمثلة:

- `saad/feature/sales-return`
- `udai/fix/invoice-validation`
- `chatgpt/review/inventory-integrity`

## دورة العمل لكل مهمة

1. حدّث `main` محليًا.
2. أنشئ Branch جديد من `main`.
3. سجّل المهمة في ملف المتابعة/Excel مع اسم المسؤول واسم الـBranch.
4. نفّذ التعديل داخل الفرع فقط.
5. قبل فتح PR، اسحب آخر تغييرات `main` إلى الفرع أو أعد ترتيب الفرع عليها حسب أسلوب الفريق.
6. شغّل الاختبارات ذات العلاقة ثم الاختبارات الكاملة عندما يكون التغيير في مسار حساس.
7. افتح Pull Request إلى `main`.
8. لا يتم الدمج إذا كانت هناك تعارضات أو اختبارات فاشلة أو نطاق غير واضح.
9. بعد الدمج، غيّر حالة المهمة في لوحة المتابعة إلى `Merged` ثم `Done` بعد التحقق.

## منع التعارض بين سعد وعدي

قبل بدء أي مهمة، يجب أن يكون لها Owner واحد أساسي وBranch واحد.

إذا كانت مهمتان تلمسان نفس الملفات أو نفس الـdomain:

- لا يبدأ الطرف الثاني تعديلًا كبيرًا قبل التنسيق.
- الأفضل تقسيم العمل حسب الملفات أو الطبقات أو التسلسل.
- إذا كان لا بد من العمل بالتوازي، افتحوا PRs صغيرة ومتكررة بدل PR ضخم.

## حالات المهام المعتمدة

- `Backlog`
- `Ready`
- `In Progress`
- `Blocked`
- `In Review`
- `Changes Requested`
- `Ready to Merge`
- `Merged`
- `Done`

## الأولوية

- `P0` — عطل حرج / سلامة بيانات / إنتاج
- `P1` — مشكلة مهمة جدًا أو مانع إطلاق
- `P2` — تحسين أو نقص مهم
- `P3` — تحسين منخفض الأولوية

## قاعدة Pull Requests

كل PR يجب أن يحتوي على:

- وصف المشكلة أو الهدف.
- الملفات أو النطاق المتأثر.
- كيف تم اختبار التعديل.
- أي مخاطر أو آثار جانبية محتملة.
- رابط/رقم المهمة من GitHub Issue إن وجد.

## العمل مع ChatGPT

ChatGPT يمكنه قراءة GitHub ومراجعة الفروع وPRs وإنشاء ملفات أو Issues أو فروع عند الطلب من خلال الربط المتاح.

لاعتبار Excel وGitHub وChatGPT منظومة واحدة:

- GitHub هو المصدر الحقيقي للكود والفروع وPRs.
- Excel هو لوحة تخطيط ومتابعة بشرية، وليس مصدرًا للكود.
- عمود `GitHub Issue / PR` في Excel يربط كل مهمة بسجل GitHub.
- عمود `Branch` يحدد مكان تنفيذ المهمة.
- عند طلبك من ChatGPT، يمكنه الرجوع إلى GitHub ومساعدتك في تحديث حالة المشروع بناءً على البيانات الحالية.

> ملاحظة: ملف `.xlsx` نفسه لا يملك مزامنة ثنائية مباشرة وآمنة مع GitHub بمجرد وجوده داخل المستودع. الأفضل حفظ نسخة Excel للاستخدام اليومي، مع اعتبار GitHub Issues/PRs المصدر الفعلي للحالة التقنية. يمكن الاحتفاظ بنسخة من ملف Excel داخل المستودع أيضًا عند الحاجة إلى snapshot/versioning.

## قبل بدء أي يوم عمل

1. راجع المهام المفتوحة.
2. تأكد أن كل مهمة لها Owner وBranch مستقل.
3. اسحب آخر `main`.
4. لا تبدأ تعديلًا على ملفات يعمل عليها الطرف الآخر إلا بعد التنسيق.
5. استخدم PR مبكرًا إذا كان التعديل كبيرًا حتى يظهر للطرف الثاني ما الذي يتغير.

## Definition of Done

تعتبر المهمة منتهية فقط إذا:

- التعديل موجود في Branch مستقل.
- الاختبارات المطلوبة ناجحة.
- تمت مراجعة PR.
- تم دمجها إلى `main`.
- تم التحقق أن النظام لم يتأثر في المسارات المرتبطة.
